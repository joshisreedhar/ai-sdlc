# Phase 4 Summary: Branding & Conversion Tracking

## 🎯 Executive Summary
Phase 4 extends the platform beyond generic short links into a branding and attribution toolset: custom domains and aliases for on-brand links, styled QR codes for offline campaigns, and a pixel-firing intermediary page that closes the attribution loop for paid acquisition. This plan is scoped and ready for development sign-off.

## 💎 Business Value Realized
- Marketing teams can present fully branded, on-domain short links (e.g., `brand.com/promo`) instead of a generic shared domain, increasing recipient trust and click-through rates.
- Visual, styleable QR codes let brands extend their identity into print and offline channels while keeping the underlying destination centrally managed.
- Native Meta/Google Ads/TikTok pixel firing enables marketers to attribute downstream conversions (signups, purchases) directly back to the campaign/ad that drove the click - a key requirement for paid acquisition budget justification.

## 📦 Scope & Deliverables
- **Custom Aliases:** User-defined, per-domain-unique slugs supplied at link-creation time, validated and resolved through the existing redirection lookup path.
- **Custom Domains:** Bring-your-own-domain onboarding with DNS-based ownership verification and domain-scoped redirection routing.
- **QR Code Generation & Styling:** On-demand generation of styled (color/shape/logo) QR codes that always encode the short URL, persisted to object storage, and unaffected by later destination changes.
- **Conversion Tracking Pixel Workflow:** An opt-in intermediary HTML page that fires configured Meta/Google Ads/TikTok pixels before performing a JavaScript-based redirect, applied only to links with pixels configured.

## 🛠️ Technical Highlights & Risk Mitigation
- Domain verification uses a DNS TXT-record challenge, keeping the platform cloud- and DNS-provider-agnostic in line with the Phase 2 cloud-native, multi-CSP foundation.
- TLS on arbitrary customer domains is provisioned via cert-manager/ACME against the Phase 2 Kubernetes ingress, avoiding a hard dependency on any single CSP's certificate service.
- QR codes are generated via `segno`/`qrcode` and stored in S3-compatible object storage per the architecture guidance; because the QR always encodes the short URL (not the destination), destination updates never invalidate a printed/distributed QR code.
- The pixel intermediary page is deliberately kept out of the hot redirection path: per the architecture guidance's Redirection Engine constraint (do not block the redirect on analytics), links without configured pixels continue to receive a direct, low-latency 301/302 redirect; only pixel-configured links are routed through the intermediary page.
- Click events remain published to the Phase 2 async analytics pipeline exactly once, whether a link resolves directly or through the pixel intermediary page, preventing double-counting.
